# Commitment format v2 and verification

v2 is the format for new registrations on preprod and local devnet; it is not a
mainnet format. v1 ([commitment-v1.md](commitment-v1.md)) stays verifiable for
the devnet transactions already made with it. Decisions: D13 (trust model), D14
(registrant binding), D15 (absence), D16 (testnet identity) in
[the MVP plan](plans/2026-10-01-preregistry-mvp.md).

## Bytes

`frame(x)` is a four-byte unsigned big-endian byte length followed by `x`.
All text is UTF-8. The SHA-256 input, in order, is:

1. `frame("cardano-ai-preregistry")`
2. Format version as uint16 big-endian (`0002`).
3. `frame(network_id)`, either `preprod:1` or `devnet:42`.
4. `frame(registrant)`: the registrant's 28-byte payment key hash.
5. A fresh 32-byte CSPRNG salt, fixed width (no length prefix).
6. `frame(RFC8785_JCS(manifest))`.

The manifest schema and parser rules are unchanged from v1. Binding the
registrant means a copy of a public commitment hash by another key never
verifies, even after the manifest and salt are disclosed (the same reason ENS
commitments include the owner).

`tests/fixtures/commitment-v2.json` holds five vectors generated independently by
`scripts/generate-vectors.py` (Python `rfc8785==0.1.4`), including one with a
different registrant. The v1 fixture is regenerated byte-identically.

## Public metadata

Label 86741. A commitment is exactly `app`, `format_version` (2), `network`,
`commitment_hash`, `reveal_deadline`. A disclosure announcement keeps its v1
fields (`app`, `format_version` 1, `kind` `reveal`, `network`,
`commitment_tx_hash`, `bundle_sha256`, `bundle_url` in 64-byte chunks).
Manifest, salt and results never appear in metadata.

Both transactions declare the registrant in `required_signers`; the ledger then
requires that key's witness. The fee input may come from any wallet key. The web
app takes the registrant from the wallet's change-address payment key before it
computes the hash.

## Reveal bundle (bundle_version 1, unchanged)

The registrant creates the bundle in the browser and hosts it (D7=A). Fields:
`bundle_version` (1), `app`, `network`, `commitment_tx_hash`, `manifest`,
`salt_hex`, `results` (`experiment_id`, `completed_runs`, `metrics`), `files`
(`path`, `sha256`, `url`) and optional `self_reported_period`
(`started_at`/`finished_at`, UTC whole seconds). Paths and experiment IDs are
unique; file hashes are SHA-256 lowercase hex of the exact bytes. The published
file is `RFC8785_JCS(bundle)` as UTF-8; its SHA-256 is the bundle hash. The
bundle carries no format version: the commitment it names decides v1 or v2.
URLs are printable ASCII, at most 512 bytes, `https` (or `http` on loopback for
local devnet runs) and without credentials.

## What a verifier trusts

Readers fetch raw transaction bytes from any source (Koios `tx_cbor`, the optional
development cache, a local file) and treat the source as untrusted.
`verify_transaction` in `src/transaction.ts` checks, from the bytes alone:

- the BLAKE2b-256 of the original body bytes equals the requested transaction hash;
- the BLAKE2b-256 of the auxiliary data equals the body's auxiliary data hash;
- `required_signers` has exactly one key, and a vkey witness for it verifies
  (Ed25519) over the body hash; that key is the registrant;
- the body uses only inputs, outputs, fee, validity bounds, auxiliary data hash,
  required signers and network id, the witness set only vkey and bootstrap
  witnesses, the transaction is phase-2 valid and the auxiliary data has no
  scripts. Collateral, redeemers, minting, certificates, withdrawals, reference
  inputs and script witnesses are rejected. One case cannot be seen from the
  transaction bytes alone: spending a native-script output whose script comes
  from another spent input's own reference script. That does not change the
  registrant, which is still the single required signer with a valid witness.

A failure that the transport could have caused (bytes that do not hash to the
requested transaction, changed metadata or witnesses, a source that is down, a
proof that does not verify) is `unavailable`: retry or use another source. A
transaction whose hash-bound body is not an app transaction is `invalid`.

Inclusion and time come from the reader's trust root:

| Network | Inclusion | Block time | Output label |
|---|---|---|---|
| preprod | Mithril v2 transaction proof; certificate chain checked against the compiled-in genesis key (`src/mithril.ts`) | from the certified slot with compiled-in era constants; any transport time is ignored | `mithril` |
| devnet | the local node's indexer confirms the transaction; bytes are the signed transactions you kept | the local indexer's block time | `local-node` (local trust) |
| local demo | in-tab simulation signed by a public demo key | browser clock | `local-demo` (not chain evidence) |

Mithril certification is not finality: the certified slot trails the tip by a
few blocks (about 5 in the spike), far less than the k-block depth after which
a block cannot roll back. This step only needs inclusion and slot; any status
that depends on finality (step 8's on-time and overdue decisions and rollback
handling) decides its own minimum depth.

Mithril assumes its genesis key and an honest majority of signing stake.
preprod and preview share one genesis key, so Mithril separates testnets from
mainnet but not preprod from preview; those two are told apart only by the
metadata and the network in the hash (D16). A transaction found but not yet
certified is `pending`. The first chain check in a browser takes about a
minute; verified certificates are then cached in that browser
([spike](plans/2026-10-01-preregistry-mvp/spike-mithril.md)).

## Verifying

`verify_commitment`, `verify_reveal` and `verify_announcement` in
`src/verifier.ts` take a `ChainReader` and a `FileFetcher`. Statuses: `match`,
`mismatch`, `network-mismatch`, `signer-mismatch`, `not-found`, `pending`,
`unavailable`, `files-unavailable`, `invalid`. Every result carries the verification boundary,
the trust boundary for its label, the registrant and whether the format binds it.
A v1 commitment that matches says that it does not bind the registrant.

The bundle and files can come from anywhere: `verify_announcement` accepts the
bundle bytes from the caller, and `with_uploads` serves uploaded files by hash
before trying their URLs. URLs are only the default source.

An announcement matches only if its witnessed registrant is the commitment's
registrant, the bundle hashes to the announced hash, names the same commitment
and network, and the reveal and every file match. The result names both the
commitment's registrant and the announcement's signer. The announcement's block
time does not prove that the files were retrievable then; their availability is
checked now.

The private draft (format version, network, transaction hash, manifest, salt)
is a local file; the application sends none of its contents to a server.

"Not found" means only that the source did not return the transaction. Proofs
show existence, not absence; any absence-based status must name its source and
can be overturned by anyone presenting the transaction with a proof (D15).
